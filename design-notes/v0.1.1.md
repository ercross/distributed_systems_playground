# v0.1.1 — Observable Failure Baseline

## Status

**Still intentionally fragile.**

This version preserves the **unbounded failure characteristics of v0.1.0**, but introduces **instrumentation and controllable failure dynamics** so that system behavior can be observed and reasoned about under load.

The system is still allowed to drown.

The difference is:

> We can now see it happening.



# Context

The system still consists of three independent services:

* **Order API** — accepts incoming HTTP requests
* **Order Processor** — consumes order work and performs business logic
* **Payment Service** — downstream dependency exhibiting latency and failure

All services communicate over HTTP and fail independently.

However, the system now includes **three major additions**:

1. **Observability**
2. **Controlled Chaos**
3. **Configurable Retries**

These additions do **not stabilize the system**.

They only make its behavior **visible and reproducible**.



# Why v0.1.1 Exists

The baseline in **v0.1.0** relied solely on **load generator results** to understand system behavior.

This has two problems:

1. Client metrics alone cannot explain *why* the system behaves poorly.
2. Distributed systems fail internally long before clients observe collapse.

This version introduces observability so that we can answer questions such as:

* Where is work accumulating?
* Which dependency is blocking progress?
* Is the system slow or stuck?
* Is work finishing or only entering the system?

In other words:

> We move from **symptoms** to **causal visibility**.



# Major Additions

## 1. Observability

Each service now exposes Prometheus metrics.

Metrics follow the **RED method** for HTTP services:

* **Rate** — request throughput
* **Errors** — failure ratios
* **Duration** — latency distributions

Additional **system behavior metrics** are exposed to track the shape of work moving through the system.

Examples include:

### Edge metrics

* request rate
* request latency
* forward goroutines in flight

### Processor metrics

* enqueue vs dequeue rate
* in-flight work
* processing outcomes
* dependency latency

### Dependency metrics

* payment outcomes
* payment latency
* bank hang counters

### Runtime signals

* goroutine counts
* process memory
* CPU usage

These metrics allow the system to be visualized in **Grafana dashboards** that reveal how failure unfolds.

The goal is not operational monitoring.

The goal is **learning how distributed systems degrade**.



## 2. Chaos Configuration

Each service now supports **runtime-configurable chaos knobs**.

These knobs simulate real-world production behavior such as:

* random latency
* partial failures
* dependency timeouts
* dependency hangs
* occasional crashes

Example chaos behaviors include:

```
random latency
timeout injection
request failures
unbounded downstream hangs
```

The Payment Service additionally simulates **bank gateway dynamics**:

* transaction declines
* insufficient funds
* dependency timeouts
* permanent dependency hangs

These behaviors mimic real production systems where dependencies are:

* slow
* unreliable
* partially degraded
* rarely completely down

Chaos is **not random noise**.

It is a way to reproduce **partial failure conditions** reliably.



## 3. Configurable Retry Executor

A reusable retry mechanism was introduced to simulate a common real-world design decision:

> Retry downstream calls when they fail.

Retries are configurable through:

* retry count
* retry delays
* retry conditions

However, retries are **not yet bounded by system capacity**.

This is intentional.

Retries without admission control can amplify load and accelerate collapse.

This behavior becomes visible during load tests.



# Load Testing Changes

The project now uses **k6 instead of Vegeta**.

Reasons for this change:

* richer runtime output
* concurrency modeling
* easier scripting
* better alignment with modern load testing practices

Load tests are located under:

```
test_tools/k6
```

The default script applies a **ramped concurrency load** to the Order API.

Example execution:

```bash
k6 run test_tools/k6/smoke.js
```

Unlike fixed-rate generators, this model increases concurrency and exposes:

* request pileups
* long latency tails
* dropped iterations

These behaviors are essential to understanding system failure dynamics.

```

```

This narrative shows how distributed systems typically degrade.



# Expected Behavior Under Load

When the load test runs with chaos enabled, the system exhibits the following pattern:

1. **The edge continues accepting requests**

   Incoming work continues entering the system.

2. **Forward goroutines accumulate**

   Order API goroutines begin waiting on downstream responses.

3. **Processor concurrency increases**

   Work moves into the processor but waits on payment.

4. **Payment dependency becomes slow or blocking**

   Some requests hang indefinitely.

5. **In-flight work grows continuously**

   Work enters the system faster than it exits.

6. **Latency explodes**

   Tail latency grows toward timeout boundaries.

7. **Partial failures appear**

   Some requests succeed, some fail, some stall.

8. **Client-side metrics deteriorate**

   Load generators begin reporting:

    * long latencies
    * request failures
    * dropped iterations

The system does not crash immediately.

It **drowns gradually**.

This is the defining characteristic of partial failure.



# Observed Failure Pattern

During load testing, the following system signals typically emerge:

### Edge

* request latency increases
* forward goroutines grow rapidly

### Processor

* in-flight work rises
* success rate becomes unstable

### Dependency

* payment transactions accumulate
* bank hangs trap work indefinitely

### Runtime

* goroutine count rises steadily
* memory usage increases slowly

This chain illustrates a core distributed systems truth:

> Failure often emerges from **waiting**, not from compute exhaustion.



# Why This Matters

Without observability, the system would only appear as:

* slow
* unreliable
* inconsistent

With observability, we can see the real cause:

> The system keeps accepting work while unfinished work accumulates.

This is the **most common failure pattern in distributed systems**.

Not crashes.

Not CPU exhaustion.

But **unbounded concurrency under partial dependency failure**.



# Lessons Learned

This version reveals several critical realities:

* Client metrics alone cannot explain system behavior
* Distributed failures propagate through waiting, not crashes
* Partial dependency failure is more dangerous than total failure
* Systems often fail because they continue accepting work they cannot complete
* Observability must exist before reliability improvements can be evaluated
