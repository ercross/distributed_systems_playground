# v0.2.0 Design Note — Admission Control

## What v0.2.0 Introduces

v0.2.0 adds one new distributed systems constraint:

> The system must stop accepting new work when it already has too much unfinished work.

In v0.1.1, the edge keeps accepting requests even when downstream work is slow, stuck, or failing.  
That allows unfinished work to accumulate without bound.

v0.2.0 changes only one thing:

> the ingress edge now has a fixed admission limit.

This version is intentionally narrow.

It does **not** add internal back-pressure.  
It does **not** add bounded worker concurrency.  
It does **not** change the business logic.

That is deliberate.

The goal is to teach the difference between:

- **controlling how much work enters**
- **controlling how admitted work flows internally**

v0.2.0 introduces only the first.


## Where the Constraint Is Applied

Admission control is implemented only at the **Order API**, which is the system ingress.

That is where the system decides:

> “Do we take responsibility for this request?”

This keeps the lesson clean:

- overload is stopped at the edge
- downstream behavior remains unchanged
- internal flow is still intentionally unsafe

This means v0.2.0 should show two things at once:

1. **presence of admission control**
2. **continued absence of back-pressure**


## Admission Control Mechanism

Admission control uses a fixed-capacity in-flight limiter.

Conceptually:

- each accepted order consumes one slot
- slots are finite
- if no slot is available, the request is rejected with **HTTP 503**

Lifecycle:

- slot is acquired before the request is accepted
- slot is released only when `forwardToOrderProcessor` exits
- retries, slow downstream calls, and hangs continue consuming the slot

This makes the controlled state explicit:

> accepted-but-unfinished forwarding work is bounded

Prometheus metrics do **not** own correctness here.

The limiter owns authoritative state.  
Metrics are exported from that state for observation only.


## What v0.2.0 Intentionally Does Not Fix

v0.2.0 does not introduce back-pressure.

Once work is admitted:

- the order API still forwards asynchronously
- the processor still dequeues and spawns a goroutine per item
- payment-facing concurrency is still not bounded
- slow downstream dependencies can still trap in-flight work

So this version should not be read as:

> “The system is now healthy.”

It should be read as:

> “The system now stops accepting infinite work, but still lacks internal pacing.”


## What This Version Should Make Visible

### Presence of Admission Control

Under sustained load:

- admission slots should fill up
- accepted rate should flatten at a ceiling
- rejected requests should rise
- 503 responses should become part of normal overload behavior

This is the new behavior.

Instead of accepting work forever, the edge now says:

> “No more. Capacity is already occupied.”

### Absence of Back-Pressure

At the same time, admitted work can still accumulate internally.

Because internal concurrency remains unbounded:

- forwarding goroutines can stay occupied
- processor in-flight work can rise
- payment calls can pile up
- useful completions can flatten even while in-flight work grows

This is the key v0.2.0 tension:

> bounded ingress does not imply controlled internal flow


## Metrics Added and Why

The metrics in v0.2.0 were chosen to make the lesson visually undeniable.

### Order API

These show **presence of admission control**:

- `order_api_orders_accepted_total`
- `order_api_orders_rejected_total`
- `order_api_validation_rejections_total`
- `order_api_admission_rejections_total`
- `order_api_admission_in_use`
- `order_api_admission_limit`

These separate:

- valid work that was accepted
- invalid work rejected by validation
- excess work rejected because admission capacity was exhausted

These also show whether admission slots are actually saturating.

The following metrics show whether admitted work is remaining stuck at the edge:

- `order_api_processor_forward_in_flight`
- `order_api_processor_forward_duration_seconds`

These matter because admission slots are held for the full forwarding lifecycle.


### Order Processor

These show **absence of back-pressure inside the system**:

- `order_processor_orders_enqueued_total`
- `order_processor_orders_dequeued_total`
- `order_processor_processing_spawned_total`
- `order_processor_in_flight`
- `order_processor_payment_calls_in_flight`
- `order_processor_queue_depth`
- `order_processor_oldest_queued_age_seconds`
- `order_processor_queue_wait_duration_seconds`
- `order_processor_processing_duration_seconds`
- `order_processor_orders_processed_total`
- `order_processor_last_processed_timestamp_seconds`

These were chosen to expose an important v0.2.0 truth:

> backlog does not have to live in a queue

Because the processor immediately dequeues and spawns goroutines, queue depth may stay deceptively low while in-flight execution explodes.

That is not a bug in the lesson.  
That is part of the lesson.


### Payment Service

These show the **downstream pressure source**:

- `payment_service_transactions_in_flight`
- `payment_service_bank_gateway_calls_in_flight`
- `payment_service_bank_hangs_in_flight`
- `payment_service_bank_hang_enabled`
- `payment_service_processing_duration_seconds`
- `payment_service_bank_gateway_duration_seconds`
- `payment_service_outcomes_total`
- `payment_service_up`

These make it possible to correlate cause and effect across the chain:

slow bank behavior  
→ trapped payment work  
→ rising processor payment calls in-flight  
→ rising processor in-flight work  
→ slow forwarding completion  
→ occupied admission slots  
→ rising admission rejections


## Chaos Configuration Changes and Why

For v0.2.0, chaos should support the lesson, not blur it.

The main rule is:

> keep the edge clean, concentrate pressure downstream

### Order API

Order API chaos should be mostly disabled.

Why:

- the edge is where admission control must be clearly observed
- random edge latency or random edge failure makes overload shedding harder to interpret

The edge should reject work because of **capacity**, not because it is flaky.

### Order Processor

Order processor chaos should be reduced to mild latency only.

Why:

- processor should remain mostly functional
- it should expose unbounded internal fan-out
- it should not become the main source of arbitrary failure noise

### Payment Service

Payment service should be the main pressure source.

Why:

- payment slowness, timeout, and hang behavior are what trap downstream concurrency
- trapped downstream work is what keeps upstream slots occupied

This creates the clean causal chain v0.2.0 needs.


## Load Test Changes and Why

The load test for v0.2.0 should not simply overwhelm the system as fast as possible.

It should make the admission transition visible.

So the test should be adjusted to:

- ramp more gradually
- cross the admission boundary progressively
- explicitly treat **201** and **503** as meaningful outcomes

Why:

- **201** shows accepted work
- **503** shows intentional overload shedding
- the goal is to watch the system move from:
    - below saturation
    - to saturation
    - to controlled rejection

This version is not a pass/fail test.

It is an observability exercise.

That is why generic failure-rate thresholds are less useful here than explicitly tracking accepted vs 503 responses.


## What You Should Expect to Observe

When the experiment is configured correctly, the dashboard should tell this story:

1. traffic keeps arriving at the edge
2. admission slots rise toward the configured limit
3. once the limit is reached, 503 admission rejections begin rising
4. forwarding work remains in-flight longer because downstream is slow
5. processor and payment in-flight work rise together
6. successful progress flattens or becomes sparse
7. runtime cost appears as rising goroutines and memory pressure

The important behavioral change from v0.1.1 is:

### v0.1.1
> accept everything and drown quietly

### v0.2.0
> accept bounded work and reject excess, while still lacking internal pacing



## What This Version Teaches

v0.2.0 teaches two truths at the same time:

> Systems that accept all work eventually fail.

and

> Bounding accepted work is not the same as pacing internal work.

This version is successful if it makes both visible.

The edge should now remain bounded.

The inside of the system should still visibly struggle.

That tension is the entire point of v0.2.0.
